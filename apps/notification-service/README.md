# Notification Service (`apps/notification-service`)

Notification management and alert dispatch microservice built with **Node.js**, **Express**, and **TypeScript**, integrating with backend services via internal endpoints and with the **Django Identity Service** for JWT user authentication.

---

## 🎯 1. Service Purpose

The **Notification Service** receives notification events generated by backend microservices (e.g. Orders Service), persists notifications, and allows authenticated users to inspect, filter, and mark their notifications as read.

---

## 📋 2. Responsibilities

- **Internal Event Ingestion**: Provide an internal API (`POST /internal/notifications`) for backend services to trigger user notifications.
- **User Notifications**: Expose protected endpoints for authenticated users to retrieve their notifications and unread counts.
- **User Isolation**: Guarantee strict user isolation so that users can never access or modify another user's notifications.
- **Read State Tracking**: Allow users to mark their own notifications as read (`PATCH /api/notifications/:id/read`).
- **Stateless JWT Authentication**: Verify HMAC-SHA256 JWT tokens issued by the Identity Service.

---

## 🛠️ 3. Technology Stack

- **Runtime**: Node.js (v20+)
- **Framework**: Express 4.x
- **Language**: TypeScript 5.x
- **Authentication**: `jsonwebtoken` (HMAC-SHA256 verification)
- **Security**: Helmet, CORS
- **Testing**: Jest + Supertest + `ts-jest`
- **Default Port**: `8003`

## 🏛️ 4. Architecture Overview

```
 [ Orders Service (Spring Boot) ]
                 │
                 │ POST /internal/notifications (Synchronous HTTP)
                 ▼
 ┌────────────────────────────────────────────────────────┐
 │ Notification Service (Express + TypeScript - Port 8003) │
 │                                                        │
 │  ┌────────────────────────┐  ┌──────────────────────┐  │
 │  │ Internal Routes        │  │ User API Routes      │  │
 │  │ /internal/notifications│  │ /api/notifications/* │  │
 │  └───────────┬────────────┘  └───────────┬──────────┘  │
 │              │                           │ (Bearer JWT)│
 │              ▼                           ▼             │
 │  ┌──────────────────────────────────────────────────┐  │
 │  │ NotificationService & Repository                 │  │
 │  │ (In-Memory / Interface-backed Persistence)       │  │
 │  └──────────────────────────────────────────────────┘  │
 └────────────────────────────────────────────────────────┘
                 ▲
                 │ GET /api/notifications (Bearer JWT)
                 │ PATCH /api/notifications/:id/read
         [ Client Frontends ]
```

---

## 🔗 5. Relationship with the Orders Service & Identity Service

1. **Identity Service**: Sits as the central auth authority. The Notification Service verifies JWTs signed with `JWT_SECRET` / `DJANGO_SECRET_KEY` and requires a valid numeric `user_id` claim (`user_id > 0`).
2. **Orders Service**: Upon order creation, the Orders Service makes a synchronous HTTP request to `POST /internal/notifications`. If this call fails, the Orders Service logs the error and proceeds without rolling back the order.

## 🗄️ 6. Notification Data Model

| Field       | Type      | Description                                   |
| ----------- | --------- | --------------------------------------------- |
| `id`        | `number`  | Auto-incremented primary key                  |
| `userId`    | `number`  | User ID from Identity Service                 |
| `type`      | `string`  | Notification type (currently `ORDER_CREATED`) |
| `title`     | `string`  | Short title summary                           |
| `message`   | `string`  | Notification text body                        |
| `read`      | `boolean` | Read status (`false` by default)              |
| `createdAt` | `string`  | ISO 8601 creation timestamp                   |

## 🚀 8. How to Run Locally

### Prerequisites

- Node.js 20+ and npm installed.

### Install & Build

```bash
cd apps/notification-service
npm install
npm run build
```

### Start Development Server

```bash
npm run dev
```

### Start Production Server

```bash
npm start
```

The service will be live at [http://localhost:8003](http://localhost:8003).

## 📖 10. API Endpoint Documentation

| Method  | Endpoint                      | Authentication         | Purpose            | Status Code      | Description                               |
| ------- | ----------------------------- | ---------------------- | ------------------ | ---------------- | ----------------------------------------- |
| `GET`   | `/health`                     | No                     | Public             | `200 OK`         | Service health check (`{"status": "ok"}`) |
| `POST`  | `/internal/notifications`     | No (Internal)          | Backend Services   | `201 Created`    | Ingest notification from other services   |
| `GET`   | `/api/notifications`          | Yes (`Bearer <token>`) | Authenticated User | `200 OK`         | Get all notifications for current user    |
| `GET`   | `/api/notifications/unread`   | Yes (`Bearer <token>`) | Authenticated User | `200 OK`         | Get unread notifications for current user |
| `PATCH` | `/api/notifications/:id/read` | Yes (`Bearer <token>`) | Authenticated User | `200 OK` / `404` | Mark own notification as read             |

## 💡 11. Example Requests & Responses

### 1. Ingest Internal Notification (`POST /internal/notifications`)

**Request**:

```bash
curl -X POST http://localhost:8003/internal/notifications \
  -H "Content-Type: application/json" \
  -d '{
    "userId": 5,
    "type": "ORDER_CREATED",
    "title": "Order created",
    "message": "Your order #12 has been created successfully."
  }'
```

**Response (`201 Created`)**:

```json
{
  "id": 1,
  "userId": 5,
  "type": "ORDER_CREATED",
  "title": "Order created",
  "message": "Your order #12 has been created successfully.",
  "read": false,
  "createdAt": "2026-08-22T06:00:00.000Z"
}
```

---

## 🔮 12. Known Limitations & Future Improvements

- **Asynchronous Message Broker**: Replace synchronous HTTP calls with message brokers (Kafka/RabbitMQ) for decoupled event streams.
- **Service-to-Service Authentication**: Secure `/internal/*` routes with mutual TLS (mTLS) or internal service tokens.
- **External Channels**: Add email (SMTP), SMS (Twilio), and WebSocket real-time push dispatchers in future phases.
- **Persistent Database**: Transition in-memory repository to PostgreSQL via TypeORM / Prisma.
