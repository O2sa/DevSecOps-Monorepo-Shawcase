# DevSecOps Web Portal (`apps/web`)

The **DevSecOps Web Portal** is the primary public client frontend of the DevSecOps Proof-of-Concept platform, built with **Next.js 14** (App Router), **React 18**, and **TypeScript**.

---

## 🎯 1. Application Purpose

The **Web Portal** serves as the user-facing interface allowing visitors and customers to:
- Browse products available in the product catalog.
- Register a user account with the **Django Identity Service**.
- Authenticate and receive stateless JWT access & refresh tokens.
- Place customer orders with the **Spring Boot Orders Service**.
- View and track personal order history.
- View real-time event notifications generated by backend microservices via the **Express Notification Service**.
- Mark notifications as read.

---

## 🛠️ 2. Technology Stack

- **Framework**: Next.js 14 (App Router)
- **UI & Logic**: React 18 & TypeScript 5
- **Styling**: Vanilla CSS with custom tokens and dark theme
- **Authentication**: Stateless Bearer JWT tokens issued by Identity Service
- **Testing**: Jest + React Testing Library + `@testing-library/jest-dom`
- **Default Port**: `3000`

## 📄 4. Pages & Routes

| Route | Access | Purpose | Integrated Backend Service |
|---|---|---|---|
| `/` | Public | Platform overview, status highlights, quick action cards | - |
| `/register` | Public | User registration form | Identity Service (`POST /api/auth/register`) |
| `/login` | Public | User login form | Identity Service (`POST /api/auth/login`) |
| `/products` | Public / Auth | Product catalog browsing and order placement | Orders Service (`GET /api/products`, `POST /api/orders`) |
| `/orders` | **Protected** | Personal order history table | Orders Service (`GET /api/orders/me`) |
| `/notifications` | **Protected** | Notifications inbox with All/Unread filter and Mark Read | Notification Service (`GET /api/notifications`, `PATCH /api/notifications/:id/read`) |
| `/api/health` | Public | Web portal health probe (`{"status": "ok"}`) | Next.js API Route |

## 🔐 5. Authentication Flow & Token Storage

1. **User Authentication**:
   - The user inputs credentials on the `/login` page.
   - The frontend calls `identityApi.login({ username, password })`.
   - The Identity Service verifies credentials and issues an HMAC-SHA256 JWT access token.
2. **Centralized Token Storage**:
   - Stored in `authStorage` (isolated `localStorage` with memory fallback), preventing ad-hoc storage manipulation across components.
   - `AuthProvider` exposes user state, `isAuthenticated`, `login`, `register`, and `logout`.
3. **Authenticated API Calls**:
   - `apiClient` automatically injects `Authorization: Bearer <token>` into outbound requests to Orders and Notification services.
   - If an endpoint returns `401 Unauthorized`, `authStorage.notifyUnauthorized()` clears stale credentials and triggers a clean re-login.

> [!NOTE]
> The frontend does **not** generate tokens or enforce backend security. The backend microservices remain the ultimate security authorities validating signatures, tenant ownership, and permissions.

## 🚀 7. How to Run Locally

### Prerequisites
- Node.js 20+ and npm.

### Installation
```bash
cd apps/web
npm install
```

### Start Development Server
```bash
npm run dev
# Live at http://localhost:3000
```

### Production Build
```bash
npm run build
npm start
```

## 🔮 9. Known Limitations & Future Improvements

- **Secure HTTP-Only Cookies / BFF**: Future security maturity phases can transition client-side token storage to a Backend-For-Frontend (BFF) proxy or secure HTTP-only cookies.
- **Server-Side Rendering (SSR) User Profile**: User state is hydrated on the client via `authStorage` and `GET /api/users/me`.
- **Admin Management**: Administrative order status updates and user administration are delegated to the Angular Admin Dashboard (`apps/dashboard`).
